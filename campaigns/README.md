# Campaigns

Private shared game notebooks are independent of character ownership and encounter Tabletops. Owners/GM manage invitations and recovery; players edit shared world notes and their own PC profiles. Existing accounts must accept invitations (seven-day expiry). Removing a member withdraws reactive signals and denies subsequent note/image requests. A native sheet or tabletop link never grants new native permissions or copies private sheet data.

Pages include PC profiles, NPCs, locations, nested places and session journals. Locations support up to eight levels, with cycle and cross-game checks. Shared/GM-only audiences apply to search, relationships, history and artwork. Hidden parents restrict descendants. Publishing a branch requires confirmation and changes history epochs; explicitly private descendants stay private. Restoring historical private text to a shared audience also requires explicit publication.

Saves stage immutable revisions and publish their IDs, history, memberships and media in one campaign-document compare-and-set. Stale revisions, including work prepared before a membership change, cannot overwrite the committed game. Client drafts are scoped to account/game/page and browser session, with cleanup on logout/account switching and revocation. Conflicts retain the draft for manual comparison and reconciliation.

Limits: five owned games/account; 30 members/game; 1,000 pages including Trash; 4 MiB current text/game; up to 50 revisions/page, within 4,000 total snapshots and 32 MiB retained history/game. Trash is retained until explicitly purged by a manager. Archived games remain readable. Permanent whole-game deletion requires ownership, archive and exact-name confirmation. Account deletion is blocked while the account owns any campaign; transfer or delete explicitly first.

Artwork: non-animated JPEG/PNG/WebP up to 4 MiB, 24 megapixels and 12,000 pixels per side; <=640px JPEG previews. 25 MiB/game, 200 assets/game and 20 attachments/page; 150 MiB total installation artwork. Uploads preserve a 3 GiB free-space reserve. Validation decodes image content rather than trusting extensions. Campaign-owned originals and previews are stored under DICECLOUD_STORAGE_PATH/campaigns on the existing files volume. Images are fetched through authenticated methods, with current permissions rechecked before returning data. No anonymous download URL or reusable access token exists. Browser previews stay in memory; no campaign bodies or images enter an HTTP shared cache.

Reusing an image within the game does not duplicate its file or quota charge. Immutable metadata versions share an original blob. Removing an attachment keeps the campaign asset. Unused assets can be removed separately. An entry upload inherits its effective audience; publishing a page does not publish its GM artwork. Explicitly publishing artwork makes it a standalone shared gallery item.

Withdrawn snapshots, assets and orphan files have a one-hour cleanup grace period; current game roots define visibility immediately. Cleanup keeps currently referenced data. Files from permanently deleted games become inaccessible immediately and are reclaimed after this grace period. Backup retention is separate. A departed player's notes and artwork stay with the group, with author attribution.

Deployment currently uses one application process. An in-process mutex bounds duplicate mutation/media work; Mongo root CAS is the correctness boundary for campaign commits. Global filesystem quota allocation assumes this single uploader process. Do not scale upload workers without a distributed quota allocator.

Back up all Mongo collections and the files volume coherently using deployment/operations.py. Restore into a fresh dicecloud-restore-* project and verify original bytes, thumbnail access, GM history, membership revocation and existing character/library records. No schema-version migration or automatic creation of real campaigns is required. Registration, DNS and proxy routing remain unchanged.
